# 時間の扱いと `temporal_id` feature

この文書は、`spatial_id` における時間機能の扱いと、`feature` による切り替え仕様をまとめるものである。

## 1. 基本方針

- 時間機能は `temporal_id` feature で切り替える（既定で有効）。
- **時間を表す専用の ID 型は作らない。** 時刻は空間 ID 型（`SingleId` / `RangeId` / `FlexId`）が
  フィールドとして直接持つ。
- 既存の空間 API は維持し、時間はその上に足す。

## 2. 公開 API に出てくる時間の型は `Interval` だけ

利用者が名前を書く時間の型は `Interval`（時間間隔 `{i}`、秒数）のみである。
「いつか」は各 ID が自分の形で持ち、平たいアクセサで読み書きする。

| | 空間 | 時間 |
| :--- | :--- | :--- |
| `SingleId` | `z` + `f, x, y`（単一） | `interval()` + `t() -> u64`（単一） |
| `RangeId` | `z` + `f, x, y`（範囲） | `interval()` + `t() -> [u64; 2]`（範囲） |
| `FlexId` | 軸ごとの `zoom` + `index` | `t_zoomlevel()` + `t_index()`（4軸目） |

```rust
let id = SingleId::new(12, 0, 3638, 1614)?.time_with(1800, 809712)?;
assert_eq!(id.to_string(), "12/0/3638/1614_1800/809712");
assert_eq!(id.interval().seconds(), 1800);
assert_eq!(id.t(), 809712);
assert_eq!(id.seconds_range(), (1_457_481_600, 1_457_483_400));
```

`SingleId` が単一の `t` しか持てないのは仕様に合わせるためである。`{t}` は単数のインデックスなので、
`12/0/3638/1614_1800/5:8` のような範囲付きの文字列は `SingleId` としては受理されない
（`RangeId` としては受理される）。

### 構築方法

| 方法 | 用途 |
| :--- | :--- |
| `SingleId::new(z, f, x, y)` | 時間を指定しない（全時間） |
| `id.time_with(i, t)` | 既存の ID に時間を付ける（ビルダー。`FlexId` は `time_with_segment(tz, t)`） |
| `id.time_with_at(i, unix秒)` | 仕様 1.5.3 (3) の `t = floor(u / i)` を内部で計算（`SingleId` のみ） |
| `range.with_time_seconds(start, end)` | 秒区間から。単位は自動で最も粗いものが選ばれる |
| `id.time_relabel(i)` | 秒区間は変えずに単位だけ変える |

`FlexId` は4軸すべてを「ズーム＋インデックス」で持つので、
`FlexId::new_with_time(fz, f, xz, x, yz, y, tz, t)` のように時間軸も同じ形で指定する。

## 3. `Interval` は「時間軸のズームレベル」である

仕様は `{i}` に任意の秒数を認めるので、`Interval::new` は `1..=2^35` の任意の値を受け付ける
（`1800` や `7200` も有効）。

### 扱える時間の範囲

`Interval::WHOLE_SECONDS = 2^35`（34,359,738,368 秒、約1089年）。起点は仕様どおり
1970-01-01 00:00 UTC なので、**3058年ごろまで**を表せる。

この値は時間軸トライの深さそのもの（最深ズームの1Segmentが1秒）なので、大きくすると
現実の時刻が深いところへ沈み、挿入・探索が遅くなる。

| `WHOLE_POW` | 表せる範囲 | 深さ |
| :--- | :--- | :--- |
| 30（空間軸と同じ） | 2004年まで | 30 |
| 31 | 2038年まで | 31 |
| 32 | 2106年まで | 32 |
| **35（採用）** | **3058年まで** | **35** |
| 62 | 1461億年後まで | 62 |

空間軸の最大ズーム（30）に揃えると2004年で尽きるため、時間軸だけは別の値になる。
`Interval::WHOLE_POW` と `TZoomLevel` の `LIMIT` が食い違わないことは `const` アサーションが
コンパイル時に保証する。

### 同一性

各 ID の `PartialEq` / `Hash` / `Ord` は `Interval` を含めた**表記の一致**を見る。
したがって次の2つは、同じ絶対秒区間を指していても等しくない。

```rust
RangeId::new(4, 0, 0, 0)?.time_with(Interval::HOUR,   [0, 0])?   // [0, 3600)
RangeId::new(4, 0, 0, 0)?.time_with(Interval::MINUTE, [0, 59])?  // [0, 3600)
```

これは空間側で
`RangeId::new(1, [0,0], [0,0], [0,0]) != RangeId::new(2, [0,1], [0,1], [0,1])`
（同じ領域だがズームが違うので別物）となるのと同じ規約である。**ID 型はリテラルな表記を保ち、
正規化はコレクション側（FlexTree の畳み込み）が担当する**という役割分担になっている。

秒区間そのもので比較したい場合は `seconds_range()` どうしを比べる。

### 交差の可換性

`intersection` は絶対秒区間で交差を取るので、`Interval` が違っても正しく比較でき、
引数の順番にも依存しない。空間側の `FlexId::intersection` が常に「深いズームの側」を選んで
可換であるのと同じ考え方である。

なお `SingleId::intersection` / `difference` の戻り値は `RangeId` である。空間の交差は必ず
単一Segmentになるが、時間の交差は単一Segmentにならないことがあるため（例: `5/1` と `7/1` の交差
`[7, 10)` は、`i = 3` かつ `t = 7/3` が必要で表せない）。

## 4. `Interval` の復元

FlexTree は時間を「2の冪秒のSegment」として持つ。`{i}` の秒数は2の冪とは限らないので、
挿入時には区間木的な分解によって複数のSegmentへ展開される（`1800` 秒なら5個）。

読み出し時は次の2段で元の表記へ戻す（`time::time_segments`）。

1. **Segment単位の復元**（`FlexId::interval()` / `t()`）
   Segmentの秒幅は必ず `2^(35 - t_zoomlevel)`、開始秒はその倍数なので、`gcd(開始秒, 幅)` は恒等的に
   幅に等しい。したがって幅をそのまま `{i}` に、インデックスをそのまま `{t}` にすれば
   厳密かつ O(1) で復元できる。
2. **区間からの復元**（`RangeId::with_time_seconds`）
   任意の秒区間 `[start, end)` については、`start` と区間幅の両方を割り切る最大の単位である
   `gcd(start, 幅)` を使う。固定候補（Day/Hour/Minute/Second）の総当たりではないので、
   `1800` / `7200` / `300` のような任意秒数もそのまま戻る。

さらに、`RangeId` / `SingleId` を書き出す経路（`flat_single_ids` と JSON 直列化）では、
書き出す前に**FlexIdと値が同じで時間が隣接するSegmentを結合**する
（`flex_tree::time_reconstruct::reconstruct_temporal`）。これにより、分解された5個のSegmentが元の
`[start, end)` に戻り、上記2の `gcd` によって `1800/809712` がそのまま復元される。

```text
入力  : 12/0/3638/1614_1800/809712
木    : 5 TimeSegment（幅 8 / 128 / 128 / 512 / 1024 秒）
JSON  : { "z":12, "f":[0], "x":[3638], "y":[1614], "i":1800, "t":[809712] }
```

`get` / `iter` のように `FlexId` を返す経路は、`FlexId` が2分岐Segment1個しか持てないため、
結合を行わず生のSegmentをそのまま返す。

## 5. feature による違い

### 無効時

- `Interval` はサイズ0のスタブになり、全時間以外を構築できない。
- 全Segmentが全時間なので、`FlexTreeCore` は F/X/Y の3次元でしか割らない。
- `time_with()` は全時間以外を受け付けない。

### 有効時

- `time_with()` / `time_with_at()` / `with_time_seconds()` で任意の時間区間を扱える。
- `intersection` / `difference` が時間も考慮する。
- `FlexTreeCore` は時間も `Dimension::T` として割る。

## 6. 文字列表現

| 型 | 形式 |
| :--- | :--- |
| `SingleId` | `{z}/{f}/{x}/{y}`、時間があれば `_{i}/{t}` |
| `RangeId` | `{z}/{f}/{x}/{y}`（各次元は `min:max`）、時間があれば `_{i}/{t}` または `_{i}/{tmin}:{tmax}` |
| `FlexId` | `{fz}/{fi}\|{xz}/{xi}\|{yz}/{yi}`、時間があれば `\|{tz}/{ti}` |

`FlexId` だけ `_` を使わないのは、`SingleId` / `RangeId` の `_` の右側が「秒数/インデックス」
であるのに対し、`FlexId` の時間は「ズーム/インデックス」で意味が違うためである。同じ記号を
使うと、`Interval` が任意秒数を許すぶん取り違えてもエラーにならず気付けない。
`FlexId` は軸ごとに `|` で並べる本来の形へ揃えてある。

## 7. 時間を使うときのコスト

時間軸は Unix 元期を起点とする2進トライで、`{i}` が2の冪でないと複数Segmentへ分解される。
同じ2000件を、時間の付け方だけ変えて挿入した実測値（`WHOLE_POW = 35`）:

| | 挿入時間 | 空間のみ比 | Segment数/件 |
| :--- | ---: | ---: | ---: |
| 空間のみ | 1.82 ms | 1.0× | 1 |
| `{i}` = 1 秒 | 4.96 ms | 2.7× | 1 |
| `{i}` = 1 時間 | 17.8 ms | 9.8× | 9 |
| `{i}` = 1 日 | 21.5 ms | 11.8× | 10 |

1秒（Segment1個）でも 2.7 倍かかるのはトライの深さ（35段）、1時間で 9.8 倍まで伸びるのは
Segment分解によるものである。**時間を指定しない ID はこの経路を通らない**ので、空間のみの
ワークロードには影響しない。

さらに縮めるには T 軸のパス圧縮（連続する単一子ノードを1段に畳む）が必要で、これは
木の中核（`insert_mut` / `collapse_equal_children` / 永続化）に手が入るため未実施である。
