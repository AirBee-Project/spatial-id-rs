`SpatialIdSet` と `SpatialIdMap` の内部では、`FlexTree` というデータ構造が空間IDを保持している。
この章では`FlexTree` とその要素である [`FlexId`](crate::FlexId) の考え方を説明する。
ライブラリの利用には必要ない内容である。

コレクションの性能は「この位置には何があるか」を調べる検索で決まる。
集合演算も Query も対象の領域と重なる要素を速く探せて初めて成り立つ。

# Octree の課題

空間をボクセルに分けて管理する方法としては、古くから Octree や Morton 順序が使われてきた。
どちらも空間を8分木のように再帰的に分割する。

Octree の強みは、検索にかかる時間が一定で済むことである。
木を根から葉まで決まった回数だけ下れば、必ず答えにたどり着く。

一方で、いびつな形を表すと大量のボクセルが要るという弱点がある。
細長い領域や、境界が複雑な形は、無数の小さなボクセルに分解されてしまう。
個々の検索は速くても、ボクセルの数が増えると、それを順に処理するループが遅さの原因になる。

# `FlexId`

`FlexTree` は、Octree の検索の速さを保ちながら、要素の数を抑えるために作ったデータ構造である。
その要素が `FlexId` である。

`SingleId` と `RangeId` は、F・X・Y の3軸が同じズームレベルを共有していた。
`FlexId` は、**軸ごとに別々のズームレベル**を持てる。
空間IDを拡張したものなので、「拡張空間ID」と呼んでいる。

文字列では軸ごとに `{ズームレベル}/{インデックス}` を `|` で区切って並べる。

```rust
# fn main() -> Result<(), spatial_id::Error> {
use spatial_id::{FlexId, RangeId};

// F と X はズームレベル 5、Y だけズームレベル 2
let flex = FlexId::new(5, 3, 5, 3, 2, 0)?;
println!("{flex}");

// RangeId にすると、Y がズームレベル 5 で 0〜7 の8個分を覆っていることが分かる
println!("{}", RangeId::from(flex));
# Ok(())
# }
```

```console
5/3|5/3|2/0
5/3/3/0:7
```

## 軸ごとのズームレベルが要る理由

`FlexId` を使うと、セグメント木と同じ原理で、同じ領域を少ない要素で表せる。

まず1次元で考える。
連続した6マスを、すべて最も細かい葉として持つと6個の要素が要る。
粗いズームレベルのノードでまとめられる部分をまとめれば、より少ない要素で同じ範囲を表せる。

![1次元での区間の分解][flextree_segment]

セグメント木では任意の区間を高々 `O(log N)` 個のノードに分解できる。
`FlexId` は、この分解を F・X・Y の3軸それぞれに独立して当てる。
直方体の領域なら、3軸の分解の個数を掛け合わせた数の `FlexId` で表せる。

![3次元での分解][flextree_flex_id]

この図では、`SingleId` なら 84 個必要な領域が`FlexId` では 6 個で済んでいる。
1軸は高々 `2 log₂ N` 個のノードに分解できるので、F×X×Y の直方体は最大でも `8 (log₂ F)(log₂ X)(log₂ Y)` 個の `FlexId` で表せる。
`SingleId` で必要な `F×X×Y` 個と比べると、領域が大きいほど差が開く。

[3章](crate::_tutorial::_03_geometry#球)の球の例でも、13万個以上の `SingleId` が`SpatialIdSet` の中では 5372 個の `FlexId` に圧縮されていた。

## 3つの型の関係

| 変換 | 結果の個数 |
| :--- | :--- |
| `SingleId` → `RangeId` | 1 |
| `SingleId` → `FlexId` | 1 |
| `FlexId` → `RangeId` | 1 |
| `RangeId` → `SingleId` | F×X×Y |
| `FlexId` → `SingleId` | F×X×Y |
| `RangeId` → `FlexId` | 高々 2 log F × 2 log X × 2 log Y |

# `FlexTree` の構造

`FlexTree` は、各ノードが1つの軸を半分に割る2分木である。
割る軸には、そのノードの中で最も粗い軸を選ぶ。そのため、各軸のインデックスが上位ビットから1ビットずつ、F → X → Y（時空間IDでは T も）の順に振り分けられていく。

木を下るとき、**対象がその軸の範囲をすでに覆っていれば、その軸の分岐を飛ばす**。
たとえば、対象の Y がそのノードの Y の範囲全体を覆っているなら、Y の分岐は作らずに F と X だけを掘り進める。
この飛ばし方によって、軸ごとにズームレベルの違う `FlexId` が木の中に生まれる。

## 点の検索は少し遅い

Octree は1段下るごとに3軸をまとめて分割するが、`FlexTree` は1段で1軸しか分割しない。
そのため、1点だけを指す `SingleId` を探すときは、同じ細かさに届くまでに Octree より多くの段を下る。
下の図は、この違いを2軸に単純化したものである。

![点に到達するまでの段数の比較][flextree_point]

## 連続した領域は速い

連続した範囲は、`FlexTree` のほうが少ない段数で表せる。
Octree は全軸をまとめて分割するので、連続した領域でも複数の葉に分かれがちである。
`FlexTree` は覆っている軸の分岐を飛ばせるので、同じ領域を1つのノードのまま表せることが多い。
ドローンの航路や障害物の多くは、連続した領域である。

![連続した領域に到達するまでの比較][flextree_aabb]

さらに、挿入の結果として隣り合う2つの子が同じ値になると、自動で1つにまとめる。
このまとめは挿入のたびに行うので、木は常に圧縮された状態に保たれる。

## ノード数の比較

こうして `FlexTree` は、Octree で索引を作るより少ないノード数で同じ領域を表せる。
1点の検索にかかる時間は増えるが、3軸分、つまり高々3倍程度にとどまる。

下の図はある建物の1mメッシュを Octree と `FlexTree` で索引にした例である。
Octree では 21243 個のボクセルが要るところを、`FlexTree` は 1527 個で表している。

![Octree と FlexTree のノード数の比較][flextree_voxel_count]

# `SpatialIdSet` と `SpatialIdMap` の違い

どちらも内部に同じ `FlexTree` を持ち、違うのは葉に値を持つかどうかだけである。

- `SpatialIdSet` は、値を持たない。
- `SpatialIdMap<V>` は、各 `FlexId` に値 `V` を持たせる。隣り合う子は、値が等しいときだけ1つにまとまる。
